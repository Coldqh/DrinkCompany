# Feature Spec 032 — Единый цикл выпуска продукта

## Проблема

Производство было разорвано между рецептами, складом, поставщиками, партиями, розливом, брендами и торговлей. Игрок видел требования, но должен был вручную искать нужный экран и повторно восстанавливать контекст партии.

## Пользователь и сценарий

Игрок выбирает напиток, видит полный план выпуска, закрывает дефицит сырья и оборудования прямо возле требования, запускает партию, проводит дегустацию и розлив, оформляет релиз и переходит к продаже.

## Наблюдаемое поведение

- производство имеет четыре раздела: план выпуска, партии, снабжение и объект;
- новая партия начинается только из плана выпуска;
- каждое требование показывает состояние: на складе, частично обеспечено, в пути или отсутствует;
- дефицит можно заказать одной командой либо отдельным действием возле позиции;
- план заранее показывает стоимость, день возможного запуска и день готовности;
- запуск недоступен до выполнения физических, финансовых и производственных требований;
- жизненный цикл партии включает дегустацию, бутылки, розлив, бренд, релиз и первый канал продаж;
- уже заказанные бутылки нельзя заказать повторно до завершения поставки.

## Критерии приёмки

- [x] Нет отдельных кнопок «Рецепты» и «Розлив», дублирующих запуск партии.
- [x] Дефицит сырья закрывается без перехода к карточке поставщика.
- [x] Заказанное сырьё отображается как находящееся в пути с ожидаемым днём.
- [x] Автоподбор учитывает цену, срок, качество, доступный объём и минимальный заказ.
- [x] Плановая сумма включает имеющееся сырьё, закупку и процесс.
- [x] Партия не запускается при занятой линии, неисправном оборудовании, превышении объёма или нехватке денег.
- [x] Упакованная партия может получить бренд и релиз внутри одного потока.
- [x] Релиз хранит выбранный первый канал продаж.

## Негативные сценарии

- поставщик не имеет достаточного объёма;
- часть сырья уже заказана;
- поставка задержана;
- бутылки уже находятся в пути;
- обязательное оборудование отсутствует или недоступно;
- объект и линия не выдерживают объём;
- денег хватает на закупку, но не на производственный процесс;
- старый релиз не содержит нового поля первого канала.

## Данные и состояние

Новый источник истины не вводится. `productionWorkflow.ts` строит производную проекцию из `GameState.production`, `SupplyState`, `FacilityState` и `FinanceState`. Заказы, партии, бренды и релизы по-прежнему изменяются существующими доменными командами.

`ProductRelease.targetChannel` необязателен для совместимости со старыми сохранениями. Для старого релиза канал выводится из позиционирования.

## API/контракты

- `buildProductionWorkflow(state, draft)` — расчёт требований, блокеров, стоимости и сроков;
- `recommendProcurement(offers, requirement, uncovered)` — выбор реального предложения;
- `ReleaseDraft.targetChannel` — обязательный первый канал нового релиза;
- `ProductRelease.targetChannel` — сохранённый канал с совместимым fallback.

## UX

Главное действие всегда одно и зависит от текущего этапа. Вторичные данные не создают новые маршруты. Требования являются рабочим списком действий, а не справочной таблицей.

## Производительность

Расчёт выполняется только для выбранного рецепта и линейно проходит по требованиям, активным заказам, складу и предложениям. Состояние не дублируется и не сохраняется.

## Миграция и откат

SchemaVersion не меняется. Старые релизы продолжают работать через вывод канала из позиционирования. При откате поле `targetChannel` игнорируется старым интерфейсом.

## Не входит в задачу

- изменение технологической симуляции;
- автоматический запуск партии после доставки;
- создание авторских коктейлей;
- автоматическая отправка релиза конкретному покупателю.
